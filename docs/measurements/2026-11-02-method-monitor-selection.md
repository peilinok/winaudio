# #258：逐进程、逐接口和方法的 API 监控选择

本票以 `84cc7aa948743721202df20076a07adf308d54c8` 为基线，复用生产 `PipelineAttachController`、`CallLogStore` 和 `SegmentSelection`。完整源码补丁、产物和执行记录的 SHA-256 见 `.scratch/implement-pipeline-2026-11-02/258/receipt.json`。本报告只涉及 #258，不代表后续完整提交、1024 条窗口、源端统计或清空功能已经交付。

## 实现边界

- 清单包含 11 个接口、25 个方法。接口与方法共同确定开关；初始化、启停和设置等 13 个控制方法默认开启，全部 12 个缓冲区与查询方法默认关闭，包括 `GetChannelCount` 和 `GetAudioEffects`。查询和缓冲区方法启用后使用现有高频通道。
- 共享布局升到 8。在一个 8 字节对齐的原子字中同时发布 25 位选择和既有 `observationGeneration`，没有引入另一套代次。x86 与 x64 使用同一发布协议。布局名称、已加载模块路径和内容哈希继续参与兼容性检查；不兼容目标提示重启。
- 初始选择在开启该段 `captureEnabled` 前发布。运行中配置由生产接收线程处理，并以专门成功／失败事件反馈，目标无需再调用音频 API；不重新注入或修改虚表。原全局 `setPumpEnabled` 广播入口已移除，手工探针和性能夹具改用明确的实例和方法集合。
- Hook 在进入原 API 前取得选择与代次的一致快照。每个原 API 恰好转发一次；关闭的方法在取时、参数展开、格式化、打包、写入和现有统计前返回。在途调用按进入时的选择完成；跨观测代次的调用不会成为新段记录。关闭 `Activate`／`GetService` 记录仍继续成功对象发现和必要安装。
- 控制器只记忆本次工具运行中每个 PID＋创建时间实例的最后成功配置。同实例重附加沿用，新实例默认。记录段保存该段最后成功配置；历史只读，旧 token 不能修改新活动段。身份、协议、失效目标或命令失败保留有效选择。
- GUI 提供附加前草稿以及当前段的接口分组方法树，明确显示草稿、发布中、成功和失败；修改后整体应用。“显示最近调用”只改变展示，调用筛选也不改变监控配置。

## 先红后绿

直接相关基线：独立真实 Hook 测试 25/25，主测试中的附加相关测试 25/25，退出码均为 0。

1. `HookServices.DefaultQueriesDoNotRecord` 在原实现失败：默认 `GetMute`／`GetMasterVolume` 写入两条记录。接入方法选择后通过。证据为 `red-default.log`／`green-default.log`。
2. SDK 假对象最初在失败时仍写出值，不能证明失败时未误读输出。按审查要求补上失败不写输出的哨兵测试后，真实生产 Hook 明确失败：capture 旧 flags `0xABCDEF01`、Activate 和 GetService 的旧输出指针被记成新产出。仅增加三处 `SUCCEEDED` 保护后通过；没有改变 xrun 统计语义，也没有把该现象称为客户崩溃根因。证据为 `red-failed-output.log`／`green-failed-output-build.log` 和最终 Hook 日志。

## 自动验证

`WinAudioHookTests` 直接编译生产 Hook，使用 Windows SDK 接口假对象、对象局部虚表与不内联调用。独立验收表逐项覆盖 25 个方法的开启／关闭、`S_OK`／`S_FALSE`／失败、合法可选空参数、this／参数／输出／HRESULT／恰好一次转发。测试专用标记证明关闭时五类记录工作均为零，正式 Hook 和计时产物不包含这些标记。

另外验证了关闭发现入口仍安装成功对象、capture/render 同名方法独立、25 方法各四种事件同步的在途切换、旧记录保留与关闭期无补录，以及两个映射视图之间 50,000 次整体配置／代次发布没有混合快照。

生产控制器测试使用真实注入的闲置子进程：没有后续音频调用也能完成配置；写索引仍为零，patch 计数及当前代次不变。错误实例、协议不匹配和旧段 token 发布失败后保留上次成功配置，同实例重附加复用选择，模拟复用 PID 的新创建时间恢复默认。模型测试验证失败不覆盖发布值、不同实例独立和历史不可写。

两配置测试顺序执行。最终相关目标构建零警告；期间遇到 GUI／探针正在被手工验收使用的 `LNK1168`，正常退出后重新链接成功，没有强行终止验收进程。只运行直接相关测试；没有把无设备测试当作真实设备证据，也没有运行本票之外的全量回归。精确退出码和产物哈希以 receipt 为准。

独立 Standards 审查提出一项 P3：移除全局高频广播后，`shouldEmit(bool)` 留下了无效参数与 `&& true`。最终只将该函数及两个调用处改为无参，并删除恒真项，不改变记录条件。此后重新构建上述四配置、重跑同一组 Hook 与定向主测试，并以重新构建的 x64 Debug／Release 产物复跑真实方法选择与音量回路。清理前补丁 SHA-256 为 `09a8530cb9070cc2afcc9fba5566301c3cf7109fe572bc0dd5e46470761031eb`；最终补丁身份见 receipt，原两轴审查结论需要结合主代理安排的最终复审阅读。

后续独立 Standards 复审发现服务测试辅助函数丢弃索引、跨两个通道寻找同名记录，可能漏检第二次 `SetMute` 未记录。最终仅修正 `test_hook_services.cpp`：辅助函数明确检查控制／高频通道及通道内精确位置，第二次 `SetMute` 必须是控制通道第 2 条且参数为 `true`，第一次为 `false`，并保留原调用转发断言。四配置只重建 `WinAudioHookTests`、各重跑 36 项通过；产品源码、生产产物与此前主测试及真实回路证据哈希均未变，因此复用其已有结果，没有重复执行。此次测试修正前的补丁、receipt 和 Hook 结果保存在 `before-test-review/`，receipt 区分本次 Hook 重跑与复用证据的执行身份。

## 真实目标与 GUI

`HookAudioProbe --method-selection` 创建两个同位数真实音频目标，走 Shared render＋真实端点 loopback；初始分别选择 `SetMasterVolume` 与 `GetService`＋capture `GetBuffer`。逐条核对记录只包含各自启用的方法；后台接收和 100 次查看切换不改变选择。随后整体改变第二个目标的方法集合，验证旧 token 失败保留有效配置，再分离／重附加验证沿用最后成功选择与历史只读。每次记录实际加载的内容寻址 DLL 路径／SHA、PID／创建时间、端点／格式、帧推进及退出码。

Debug 与 Release 分别保存 `real-method-selection-*-native.*`。`shouldEmit` 清理后最终 Debug 两目标分别完成 206／205 次循环、154080／153600 帧，Release 分别完成 210／212 次循环、156960／158400 帧；均为 `48000 Hz / 2 ch / 32 bit / WAVE_FORMAT_EXTENSIBLE`，API 失败为 0，四个目标退出码均为 0。这些数值仅证明本轮回路持续推进，不是最终性能验收。清理前的原始 receipt 与真实回路证据另存 `before-p3/`，没有把较早回路作为本轮最终产物的运行证据。

`AttachVolumeProbe` 另以真实音量／静音方法调用和读回验证 ABI，查询方法在探针中明确启用，不靠默认值。Debug／Release 各四个方法均为 `behavior_match=1`、`matching_calls=1`，探针退出码均为 0。

GUI 验收由主代理使用生产界面完成。首轮 `gui-evidence/` 使用较早的冻结产物，早于三处失败输出保护与遗留广播入口清理；A 配置成功，B 的动态应用操作遇到夹具 20 分钟到期正常退出，不能算作 B 应用成功。

## 保留的范围

本票没有改变既有传输槽位的完整提交机制和窗口容量，也没有实现源端逐方法累计统计、1024 窗口或显式清空。相关风险及验收由 #259／#260／#261 承担。共享传输仍有既有丢失／未完整提交边界，真实回路中出现记录不等于证明全历史完整。

本票的关闭成本结论是记录步骤新增为零；选择读取、原调用和成功对象发现仍有成本。最终性能归专门验收票。本轮没有通过改断言或修复无关硬件测试扩大范围。
