# 不同 COM 实现的安全转发与有限覆盖验收

关联执行票：[#254](https://github.com/peilinok/winaudio/issues/254)。基线提交：`6dc338c80114a257743d4c30649eec92a981d7d4`。本轮只交付原函数转发、安装并发、COM 配对及 DLL 身份；没有把这些风险声称为用户应用崩溃的已确认原因。

## 交付行为

- 每个方法仅接受首个已发布的原实现地址。另一对象的同方法原地址不同，修改前拒绝该槽位，原 API 仍由该对象正常执行。相同地址的共享虚表、重复安装继续支持。允许同一对象部分方法被覆盖，不能把同 IID 当成兼容证明。
- 原方法通过 Interlocked 发布并读取，先发布原方法、再原子替换虚表指针。已有 Hook 却没有有效原函数的槽位被拒绝，不保存 Hook 自身作为原函数。
- 同一个 Hook 安装实现中的页保护修改、槽位替换及保护恢复串行执行。音频转发不获取安装锁，不分配内存。不修改可执行代码字节，因此不再对虚表数据调用 FlushInstructionCache。
- 修改前固定原实现所在模块与 Hook 所在模块，直到目标进程结束；没有保存目标对象／接口指针或永久 AddRef。对象和其私有虚表的寿命仍由目标维护；分离只停止记录，不卸载或还原 Hook。
- 模块固定在安装锁内、确认原实现兼容后执行；不会因为发现一个不支持的不同实现，就提前永久固定其模块。
- 页权限恢复失败时，在锁和当前对象仍有效的范围内立即再尝试一次清理，并保留首次失败结果。若仍无法恢复，安装器在本进程内持续报告失败，覆盖诊断要求重启目标；不保存页地址供以后修改，防止对象释放或地址复用。已安装 Hook 仍正确转发原 API，但权限未恢复本身仍是故障，工具不会将其自称为已修复或在重复安装时报告成功。
- CoInitializeEx 的 S_OK、S_FALSE 都正确配对 CoUninitialize；RPC_E_CHANGED_MODE 沿用原 apartment，不假称已经切成 MTA，也不解除已有初始化。
- 共享协议升级至第 6 版，在原字段之后追加安装诊断：成功安装尝试数、拒绝尝试数、最近拒绝的 Win32 错误以及“仅已发现实现”标志。成功数包含重复验证，不是唯一方法数或对象数。安装就绪仅表示本轮安装结束，不承诺所有 Core Audio 对象或未来不同实现都被覆盖。
- 控制器提供 `OnDemandAttach::coverage()` 快照。初次附加明确记录有限覆盖和诊断；后续拒绝在接收维护时报告到现有日志。AttachSmoke 同时打印当前覆盖诊断，因此拒绝不只存在于安装线程的返回值。
- 暂存 DLL 使用实际二进制的 SHA256 命名，并核验既有暂存副本内容。注入前检查目标的全部 WinAudioHook 命名模块；发现路径／内容身份不一致就拒绝并提示重启目标，不叠加另一份 DLL。匹配且就绪的常驻 DLL 直接复用，不再增加 LoadLibrary 引用。源 DLL 缺失也直接失败，没有复用未核验旧文件的例外。

## 缺陷判红

证据目录：`.scratch/implement-pipeline-2026-11-02/254/`。回归使用 SDK 声明的 IAudioCaptureClient 对象，通过真实接口虚调用进入生产 Hook，没有复制一个错误算法作为替身。

| 回路 | 旧生产路径结果 | 修复后结果 |
| --- | --- | --- |
| A→B、B→A 不同实现 | 第二实现的帧数、位置、QPC 和 ReleaseBuffer 输入处理误用第一实现的常量；两个方向均失败 | 支持的槽位正确转发，不支持槽位保持原方法；this、输入、输出、S_OK／S_FALSE／E_FAIL 及调用次数保持 |
| 同页两个安装者 | 保留纯观测调度点，恢复旧生产安装算法后，第二安装者在首个恢复保护前进入，实际重叠次数为 2 | 第二安装者在保护区之外等待，重叠为 0，最终页面仍为 PAGE_READONLY；发布后立刻调用也可正确转发 |
| 线程已有一次 MTA 初始化 | 恢复旧 `needUninit == S_OK` 后，安装遗漏 S_FALSE 配对，解除原初始化后再进 STA 得到 RPC_E_CHANGED_MODE | 原初始化解除后 STA 初始化为 S_OK；已有 STA 的 RPC_E_CHANGED_MODE 分支也保持原 apartment |

对应日志：`red-forwarding.log`、`red-concurrency.log`、`red-com.log`。判红时仅临时恢复相关旧生产实现，随后恢复修复版；未切换或回退用户的六槽补丁。另验证已有 Hook 且没有原方法时拒绝递归，以及一个实现已安装后另一张只读映射页保护失败：拒绝被计数，已安装和未修改的原 API 都继续可调用。

独立审查补充发现了恢复失败的重复安装误报。生产调用边界注入一次恢复失败与持续两次失败，初版分别遗留 RWX 并让重复安装返回成功；`restore-red.log` 保存两项判红，修复后的 `restore-green.log` 为 2/2。持续失败使用独立测试子进程隔离，核对原 API 的 this、输出与恰好一次调用，以及未恢复权限、后续安装仍失败和需要重启的覆盖标记。模块枚举的 First／Next 每次调用也补齐 PID、句柄、返回值与立即保存的符号错误日志。

另外，通过真实已附加目标的共享映射输入一个运行中发生的安装故障，再分离并重附加。`reuse-fault-red.log` 证明初版会错误复用、重新开启 capture；修复后，即使安装就绪标志仍为 Ok，也会在接受记录前拒绝并提示重启。安装状态已经 Failed 的常驻故障同样保留重启提示。该控制器回归对共享状态输入建模，恢复故障的生产来源则由前述安装器回归独立证明。

## 四配置结果

本机使用 Visual Studio 18 2026 的现有 x64／x86 构建缓存。CI 仍使用仓库既定的 VS 2022 配置，没有修改 preset 或 CI。

| 架构／配置 | Hook 无设备回归 | 附加／身份／远程资源相关回归 | 真实同位数静音播放目标 |
| --- | --- | --- | --- |
| x64 Debug | 23/23 | 24/24 | 目标退出 0，2 条控制、64 条泵窗口、0 xrun |
| x64 Release | 23/23 | 24/24 | 目标退出 0，2 条控制、64 条泵窗口、0 xrun |
| x86 Debug | 23/23 | 24/24 | 目标退出 0，2 条控制、64 条泵窗口、0 xrun |
| x86 Release | 23/23 | 24/24 | 目标退出 0，2 条控制、64 条泵窗口、0 xrun |

上述本地 23 项中，6 项 HookServices 属于原有未提交六槽补丁，留待 #243 独立交付；本票新增 9 项 HookForwarding，加上已提交的 8 项 HookBuffer，在本票独立提交中为 17 项。不同实现和并发回归使用捕获接口，不依赖未提交的六槽改动才能通过。

真实注入回归先向自有目标加载一份无 Hook 行为、名称模拟旧身份的 DLL；当前控制器必须在新注入之前拒绝，检查后目标仍只加载该夹具，正常退出为 0。此回路验证身份拒绝机制，不冒称兼容某个旧版产品 DLL。源文件更新会得到不同暂存路径；篡改既有副本被拒绝；源缺失不能回退到旧副本。

原 #253 即时／取消后迟到加载失败回归继续执行。其控制器目录现在放置可哈希但无效的 PE 文件：生产暂存成功后，真实远程 LoadLibrary 失败；迟到场景仍由 loader gate 保持远程线程，在线程出现后取消，再放行并确认收尾。未通过“源文件事先缺失”绕过远程失败路径。

四次 AttachSmoke 都核验 WaitForSingleObject 成功及 GetExitCodeProcess，目标退出均为 0，而不是仅依据探针父进程退出或日志非空判断。每次报告 76 次成功安装尝试、0 次拒绝，并明确是已发现实现的有限覆盖。

原始结果包括各配置构建日志、`*-final-hook.log`、`*-final-core.log`、`*-exits.json` 和 `*smoke*.log`。`artifact-manifest.json` 保存实际 DLL、测试和目标二进制的 SHA256 与时间，`system.json` 保存系统身份。最终本地源码／工作区差异另存 `working-diff.patch`；正式评审与 CI 必须以实际提交为准。

审查修复后四配置的 23 项 Hook、24 项原有相关场景和真实播放检查见 `review-fix-final-*`。最后补充的常驻故障重附加分支四配置另各执行 1/1，见 `reuse-fault-*-green.log`；它使相关测试总数增加为 25 项，没有因此重复执行无变化的其他场景。
